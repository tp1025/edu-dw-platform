# 实验报告：语义层对 Text2SQL 准确率的影响

> 实验日期：2026-11-18 ｜ 数据库：`edu_dw`（MySQL 26.10 @ 3307）
> 模型：`deepseek-chat`，temperature=0 ｜ 评测集：20 条（含标准 SQL）
> 数据来源：`results/naive.json`、`results/semantic.json`

---

## 一、实验设计

| 项 | 内容 |
|---|---|
| 任务 | 在教务学情数仓（`edu_dw`）上做自然语言取数 |
| 数据基础 | 8 张 ADS 指标表 + 4 张 DWS 主题宽表 |
| 评测集 | 20 条自然语言问题，每条配人工标准 SQL |
| 模型 | `deepseek-chat`，`temperature=0`（保证可复现） |
| **自变量** | **仅 schema 描述的丰富程度**（System Prompt 与问题文本完全一致） |
| 因变量 | 执行成功率 / 结果一致率（结果集归一化比对） |

### 两组对照

| 组 | 给模型的信息 | Prompt 长度 |
|---|---|---|
| **A 组（naive）** | 表名 + 字段名 + 类型（等价 `SHOW COLUMNS`） | **3,405 字符**（约 1.7k tokens） |
| **B 组（semantic）** | 完整语义层：字段含义 + **口径** + **枚举值** + 表粒度 + 表间关系 | **13,212 字符**（约 6.6k tokens） |

> 两组 Prompt 的唯一差异是 schema 部分。B 组多出的 9.8k 字符，全是"业务知识"。

---

## 二、总体结果

| 指标 | A 组 naive | B 组 semantic | 提升 |
|---|---|---|---|
| 执行成功率 | **75.0%** (15/20) | **100.0%** (20/20) | **+25.0 pp** |
| **结果一致率（严格）** | **60.0%** (12/20) | **85.0%** (17/20) | **+25.0 pp** |
| 结果一致率（宽松） | 65.0% (13/20) | **100.0%** (20/20) | **+35.0 pp** |

> **口径说明**
> - **严格**：列数、列顺序无关，但"值集合"必须完全一致
> - **宽松**：允许生成结果多返回列（例如多带了个 `course_name`），只要标准答案的值都在里面
>
> 两个口径都报，是因为"多返回一列"和"算错数"的严重程度不同。

### 一句话结论

> **仅补充字段语义与口径约束（不改模型、不改问题），结果一致率从 60% 提升到 85%（+25pp），
> 执行成功率从 75% 提升到 100%（+25pp）。**
> Text2SQL 的瓶颈不在模型能力，而在**语义层有没有把业务口径讲清楚**。

## 三、按题型拆分（最能说明问题的一张表）

| 题型 | 条数 | A naive 严格 | B semantic 严格 | A 宽松 | B 宽松 |
|---|---|---|---|---|---|
| 单表聚合 | 5 | 4/5 | **5/5** | 4/5 | 5/5 |
| 分组排序 | 4 | 3/4 | 3/4 | 3/4 | 4/4 |
| 明细查询 | 3 | **0/3** | **1/3** | 0/3 | 3/3 |
| 趋势对比 | 3 | 2/3 | **3/3** | 3/3 | 3/3 |
| **口径陷阱** | 3 | **1/3** | **3/3** | 1/3 | 3/3 |
| 应拒绝 | 2 | 2/2 | 2/2 | 2/2 | 2/2 |

### 三个关键观察

**① 明细查询：0/3 → 1/3（严格），0/3 → 3/3（宽松）**

A 组 3 条明细查询**全部执行失败**，B 组 3 条都能跑出正确数据。
原因见下一节——**全部是同一个幻觉字段**。

**② 口径陷阱：1/3 → 3/3**

这是差距最大、也最能证明语义层价值的一类。
A 组只对了 1 条（靠运气），B 组全对。

**③ 应拒绝题：2/2 → 2/2（无变化）**

两组都能正确拒绝敏感信息查询。
**说明**：安全约束写在 System Prompt 里就够了，不依赖语义层——这是个诚实的反例。

## 四、失败案例分析（真实数据）

### 案例 1：A 组 5 次执行失败，全是同一个幻觉字段 ⭐ 最有说服力

A 组 5 条 `EXEC_FAIL`，错误信息**完全一致**：

```
(1054, "Unknown column 'term_name' in 'where clause'")
```

| 题号 | 模型生成的 SQL（片段） |
|---|---|
| Q03 | `FROM dws_student_term WHERE term_name = '2025-2026学年第二学期'` |
| Q08 | `FROM ads_teacher_workload WHERE term_name = '2025-2026学年第二学期'` |
| Q10 | `FROM dws_student_term WHERE student_no='S013172' AND term_name = '...'` |
| Q11 | `FROM ads_student_risk WHERE term_name = '2025-2026学年第二学期'` |
| Q17 | `FROM dws_student_term WHERE student_no='S013172' AND term_name = '...'` |

**根因**：

A 组看到的 schema 是 `term_id(int)`，**没有任何信息告诉它 `202601` 是哪学期**。
模型为了按"2025-2026学年第二学期"过滤，就**编造了一个 `term_name` 字段**。

而 `dws_student_term` / `ads_teacher_workload` / `ads_student_risk` **确实没有 `term_name` 字段**
（只有 `ads_term_kpi`、`ads_term_trend` 有）。模型不知道这个区别。

**B 组如何修复**：语义层里写了

```yaml
- name: term_id
  enum:
    202501: 2024-2025学年第二学期（春）
    202502: 2025-2026学年第一学期（秋）
    202601: 2025-2026学年第二学期（春）
```

模型直接知道该用 `term_id = 202601`，**5 次执行失败全部消失**。

---

### 案例 2：Q18 —— 单位错误（89.59 vs 0.8959）

**问题**：2025-2026学年第二学期全校的通过率是多少？

**A 组生成**：
```sql
SELECT ROUND((1 - fail_rate) * 100, 2) AS pass_rate
FROM ads_term_kpi WHERE term_name = '2025-2026学年第二学期';
```

**结果**：`89.59`　**标准答案**：`0.8959`

**错在哪**：多乘了 100。模型不知道该字段是"小数"还是"百分数"。

**B 组如何修复**：语义层全局约定里写了

```yaml
rate_unit: 所有 *_rate 字段都是【小数】（0.1048 表示 10.48%），不是百分数
```

B 组输出 `0.8959`，正确。

---

### 案例 3：Q17 —— 口径陷阱（A 组选错字段）

**问题**：学号 S013172 的【**正考口径**】平均分是多少？

该生真实数据：4 门课正考挂科、均补考通过

| 口径 | 字段 | 值 |
|---|---|---|
| 最高分口径 | `avg_score` | **87.71** |
| 正考口径 | `avg_first` | **64.86** |

**A 组生成**：`SELECT avg_score FROM dws_student_term WHERE ...` → **选错字段**
（而且因为 `term_name` 幻觉，这条直接执行失败）

**B 组生成**：`SELECT avg_first ...` → **正确（64.86）**

**为什么 A 组必错**：naive schema 里两个字段都只是 `decimal` 类型：

```
avg_score(decimal(5,2)), avg_first(decimal(5,2))
```

模型无从区分。而 B 组有两个字段的口径说明：

```yaml
- {name: avg_score, cn: 均分-最高分口径, caliber: 同一班次多次考试取最高分}
- {name: avg_first, cn: 均分-正考口径,   caliber: 只取正考成绩}
```

## 五、失败模式归纳

| 失败类型 | A 组 | B 组 | 典型原因 |
|---|---|---|---|
| `EXEC_FAIL` | **5** | 0 | 幻觉字段（`term_name`） |
| `RESULT_MISMATCH` | **2** | 0 | 单位错误（×100）、列不匹配 |
| `PASS_LENIENT`（多返回列） | 1 | 3 | 不影响正确性 |

**核心结论**：A 组的 7 条失败中，**5 条（71%）是同一个根因**——模型不知道 `term_id` 的业务含义。

## 六、结论与反思

### 得到的结论

1. **语义层是 Text2SQL 的主要瓶颈，不是模型能力**
   同一个模型、同一批问题，只改 schema 描述，一致率 +25pp、执行成功率 +25pp。

2. **口径类问题必须靠语义层解决**
   "平均分"有两个口径、"通过率"要 1-`fail_rate`、"ratio 是小数还是百分数"——
   这些**从字段名完全推不出来**，只能写进语义层。

3. **安全约束不依赖语义层**
   应拒绝题两组都 100% 正确，因为约束写在 System Prompt 里。
   这说明**不同类型的知识要放在不同的地方**：口径放语义层，安全策略放 System Prompt。

### 这个 demo 的局限（面试要主动说）

| 局限 | 说明 |
|---|---|
| 评测集只有 20 条 | 统计意义有限，只能看趋势；更大规模需自动生成 + 人工复核 |
| 单模型单轮 | 没有 self-consistency（多次采样投票），也没有 few-shot 示例 |
| 表结构简单 | 只有 12 张表；真实企业数仓几百张表，需要**检索式 schema 选择**（不可能全塞进 Prompt） |
| 无错误自动修复 | 真实系统会把 SQL 执行报错回传给模型重试，本 demo 只做一次生成 |
| 两组 Prompt 长度差异大 | 成本不可比：B 组每次调用输入 token 约为 A 组的 3.9 倍 |

### 如果继续做

1. **加执行报错自修复**：把 `1054 Unknown column` 这类错误回传，让模型重写（预计能救回 A 组 5 条里的 3—4 条）
2. **加 few-shot 示例**：每类题型给 1 个示例，看能否补齐"明细查询"这个短板
3. **测成本**：对比"模糊的语义层 + 大模型" vs "精确语义层 + 小模型"，找性价比最优点
4. **规模扩展**：把 ODS/DWD 也纳入，测 schema 检索（几百张表）场景

## 七、面试话术（可直接背）

> "我在自己做的教务数仓上做了个 Text2SQL 的评测。**核心发现是：准确率上不去，通常不是模型不行，是语义层没把口径讲清楚。**
>
> 我设计了两组对照：A 组只给模型表名和字段名，B 组给完整的语义层——包括字段的业务含义、**指标口径**、以及 `term_id` 的枚举值（202601 对应哪个学期）。
>
> 结果：同一批 20 条问题，结果一致率 **60% → 85%**，执行成功率 **75% → 100%**。
>
> 最有意思的是失败归因：A 组 7 条错误里有 5 条**是同一个原因**——因为 schema 里只有 `term_id` 没有枚举值，模型就**幻觉出一个 `term_name` 字段**来筛学期，结果 SQL 直接报字段不存在。B 组把枚举值写进去以后，这 5 条全消失了。
>
> 另外我做的是**结果集归一化比对**，不是看它跑通就算对。因为跑通但口径错，是数据开发最危险的情况——报表看着正常，数字全是错的。
>
> 这个 demo 的局限我也清楚：只有 20 条题、单模型单轮，真实场景还需要 schema 检索和执行报错的自修复。"

## 八、复现方式

```powershell
cd nl2sql
$env:MYSQL_PWD = '你的数据库密码'
$env:DEEPSEEK_API_KEY = 'sk-xxx'

python runner/check_golden.py                                # 校验评测集（不花钱）
python runner/run_eval.py --mode naive    --provider deepseek
python runner/run_eval.py --mode semantic --provider deepseek
python runner/report_md.py                                   # 重新生成本文的表格
```

或直接用一键脚本：`powershell -ExecutionPolicy Bypass -File .\run.ps1`
