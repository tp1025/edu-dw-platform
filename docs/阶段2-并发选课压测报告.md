# 阶段2 实验报告：选课并发压测（500 并发零超选）

> 环境：MySQL 26.10 @ 127.0.0.1:3307 ｜ 工具：`mysqlslap`（MySQL 自带）｜ 数据：48 万选课、720 班次
> 结论：**500 并发下零超卖、零重复选课、扣减计数与实际流水完全一致**；对照组（先查后改）验证了"数据库约束是最后一道防线"。

---

## 一、三层防护设计

```
第 1 层：应用层 —— 原子 UPDATE（正确性的主力）
  UPDATE course_schedule
     SET current_count = current_count + 1
   WHERE schedule_id = ? AND current_count < max_count;
  → 「判断 + 扣减」一条语句完成，靠 InnoDB 行锁串行化
  → ROW_COUNT() = 0 说明没抢到

第 2 层：数据库约束 —— CHECK (current_count <= max_count)（兜底）
  → 即使代码写错（先查后改），也超不出去
  → 代价：超卖尝试会变成 SQL 异常，而不是静默成功

第 3 层：唯一键 —— uk_active (term_id, student_id, schedule_id, active_flag, deleted_at)
  → active_flag 生成列：有效选课=1，已退=NULL
  → 同一学生同一班次只能有一条有效选课
```

**事务边界**：扣减 + 插入在同一事务；插入失败（如唯一键冲突）→ `ROLLBACK` → **扣减自动回退**。

---

## 二、三个实验场景与结果

### 场景 A：同一学生 500 并发抢同一班次（防重复选课）

```bash
mysqlslap -h 127.0.0.1 -P 3307 -u root --protocol=TCP \
  --concurrency=500 --iterations=1 --create-schema=edu_online \
  --query="CALL sp_select_course(5001, 1, 202501, @c, @m)"
```

| 指标 | 结果 |
|---|---|
| 并发数 | 500 |
| 耗时 | **1.96 秒** |
| `current_count` | **0 → 1**（只 +1，不是 +500）|
| 选课流水条数 | **1 条** |
| 结论 | 499 次失败全部 `ROLLBACK`，扣减没有残留 ✅ |

> **关键**：如果先 `UPDATE` 再插入失败却忘了回滚，`current_count` 会变成 500 而实际只有 1 条流水——**"计数虚高"比"超卖"更隐蔽**。

### 场景 B：500 个不同学生抢 150 个名额（防超卖）

```bash
mysqlslap ... --concurrency=500 \
  --query="CALL sp_select_course(FLOOR(1+RAND()*20000), 2, 202501, @c, @m)"
```

| 指标 | 结果 |
|---|---|
| 并发数 | 500 ｜ 容量 150 |
| 耗时 | **1.83 秒** |
| `current_count` | **150**（= max_count，满载）|
| 实际流水 | **150**（与计数一致）|
| 超卖班次数 | **0** |
| 重复选课数 | **0** |

### 场景 C：对照组 —— 「先查后改」的错误实现

```sql
-- ❌ 错误做法
SELECT current_count, max_count INTO v_cur, v_max FROM ...;   -- 先查
IF v_cur < v_max THEN
   DO SLEEP(0.01);                                            -- 模拟业务耗时
   UPDATE ... SET current_count = current_count + 1;           -- 再改
   INSERT INTO selection ...;
```

| 指标 | 结果 |
|---|---|
| 500 并发 / 容量 150 | 产生**大量超卖写入尝试** |
| 最终 `current_count` | 150（没有超过）|
| 但 | **全部超卖尝试被 `ck_cs_count` CHECK 拦截 → 抛 SQL 异常** |
| 结论 | 没有 CHECK 约束的话就是**真实超卖**；有 CHECK 则变成"大量报错" |

> **这是最值钱的发现**：先查后改在并发下**必然**超卖，只不过这道题被数据库 CHECK 兜住了。**约束能挡住错误，但挡不住糟糕的设计**——用户会看到一堆报错，而不是"名额已满"这种友好提示。

## 三、面试必答的 5 个问题

### Q1：怎么防超卖？

> "三层：① 应用层用 `UPDATE ... WHERE current_count < max_count` 的原子更新，把'判断+扣减'合成一条语句，靠行锁保证原子性；② 数据库加 `CHECK (current_count <= max_count)` 兜底；③ 唯一键防同一学生重复选课。三层里第 ① 层是主力，②③ 是兜底。"

### Q2：为什么不能"先 SELECT 判断，再 UPDATE"？

> "两个事务可能同时读到 `current=149, max=150`，都判断'有余额'，然后各自 +1 → 变成 151，超卖。这就是经典的 **check-then-act 竞态**。我做对照组验证过：500 并发下它真的会产生超卖写入，只是被我加的 CHECK 拦住了。"

### Q3：`ROW_COUNT() = 0` 有几种含义？怎么区分？

> "两种：**名额已满** 和 **班次不存在**。我额外 `SELECT COUNT(*)` 查一次班次是否存在来区分，返回码设计成：0成功 / 1名额满 / 2重复选课 / 3班次不存在。这样前端能给出精确提示，而不是笼统的'选课失败'。"

### Q4：扣减成功了但插入失败，名额怎么回退？

> "同一个事务里，插入失败触发 `EXIT HANDLER FOR SQLEXCEPTION` → `ROLLBACK` → 扣减自动回退。场景 A 就是证据：500 并发只成功 1 次，`current_count` 最终是 1 不是 500。"

### Q5：怎么证明零超选？

> "三条 SQL：① `SELECT COUNT(*) FROM course_schedule WHERE current_count > max_count` = 0；② 按 (学生,班次,学期) 分组 `HAVING COUNT(*)>1` = 0；③ 逐班对比 `current_count` 与实际流水数，差值全为 0。压测后实测三项全部为 0。"

## 四、可直接写进简历的表述

> - 实现选课**存储过程**：以原子 `UPDATE ... WHERE current_count < max_count` 完成"判断+扣减"，配合唯一键兜底与事务回滚，避免 check-then-act 竞态；
> - 用 `mysqlslap` 压测 **500 并发**：同一学生重复选课场景下 `current_count` 仅 +1（499 次失败全部回滚）；500 学生抢 150 名额场景下**零超卖、零重复、计数与流水完全一致**，单轮耗时约 2 秒；
> - 通过**对照组实验**证明"先查后改"在并发下会产生超卖写入，由数据库 `CHECK` 约束拦截，验证了应用层校验与数据库约束的互补关系。

## 五、遗留与改进方向（面试可当作"我知道局限"）

| 遗留点 | 说明 | 改进 |
|---|---|---|
| 单个班次行锁竞争 | 热门班次所有请求争同一行，高并发下会排队 | 分段库存（把 150 个名额拆成 3 段），或用消息队列串行化 |
| `SLEEP` 是人工延迟 | 对照组用 10ms 模拟业务耗时 | 真实系统里网络 + 业务逻辑耗时更长，超卖只会更严重 |
| 未测死锁 | 当前所有事务加锁顺序一致（先 schedule 后 selection），未触发死锁 | 可造"反向加锁顺序"的事务验证死锁，并演示 `innodb_deadlock_detect` |
| 重试机制 | 名额满直接返回失败 | 生产可加有限重试 + 排队令牌 |
