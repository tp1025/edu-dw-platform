# 项目总览：高校学情数据平台（四层数仓）

> 更新时间：2026-11-11 ｜ 环境：MySQL 26.10 @ 127.0.0.1:3307
> 一句话：**把教务业务库（OLTP）改造成可分析的数仓（OLAP），从 200 万行明细数据里算出 8 类可交付的指标。**

---

## 一、整体架构

```
┌─────────────────────────────────────────────────────────────┐
│  源系统（OLTP） edu_normal + edu_online                      │
│  21 张表 ｜ 392 万行 ｜ 5 张 RANGE 分区 ｜ 23 条 CHECK         │
│  角色：模拟学校真实教务系统，学生选课、录成绩、点名都写这里      │
└──────────────────────────┬──────────────────────────────────┘
                           │ ① 全量贴源（INSERT...SELECT）
┌──────────────────────────▼──────────────────────────────────┐
│  ODS 层  17 张表 ｜ 289 万行                                  │
│  角色：原始留痕。全字段 VARCHAR、无约束、带批次字段             │
└──────────────────────────┬──────────────────────────────────┘
                           │ ② 清洗 + 星型建模 + 拉链
┌──────────────────────────▼──────────────────────────────────┐
│  DWD 层  15 张表 ｜ 290 万行                                  │
│  10 张维度 + 3 张事实 + 成绩宽表 + 学生拉链表                  │
│  角色：干净、可关联、可回溯的业务明细                           │
└──────────────────────────┬──────────────────────────────────┘
                           │ ③ 按主题聚合
┌──────────────────────────▼──────────────────────────────────┐
│  DWS 层  4 张宽表 ｜ 6.2 万行                                 │
│  学生×学期 / 课程×学期 / 班级×学期 / 教师×学期                 │
│  角色：把明细压成"一行一人一学期"，口径固化的中间层              │
└──────────────────────────┬──────────────────────────────────┘
                           │ ④ 面向场景出指标
┌──────────────────────────▼──────────────────────────────────┐
│  ADS 层  8 张指标表 ｜ 1.0 万行                                │
```

## 二、四层各做了什么、效果如何

### ① ODS 层（Operational Data Store）——「原始档案室」

| 做了什么 | 效果 |
|---|---|
| 17 张源表全量复制成 `ods_*` | 行数 17/17 与源表**完全一致** |
| 数值字段全部脱成 `VARCHAR` | 成绩 `-5` / `150` / `缺考` 都能原样装下（若用 DECIMAL 会直接报错丢数据） |
| 去掉所有主键/唯一键/CHECK | 源库的重复选课、脏数据能顺利进入，不被拦截 |
| 加 `src_table` / `etl_time` / `dt` | 每条数据可追溯到"从哪来、什么时候抽的、属于哪个批次" |
| 行数 + CRC32 双重对账 | 17 张表全部通过，能证明"没漏抽、没改数" |

**为什么不直接查业务库？**
业务库有 23 条约束、5 张分区表、生成列——一旦数据出问题（比如成绩录入错误），你既不敢改也不敢删。ODS 是**只读快照**，随便折腾不影响线上。

### ② DWD 层（Data Warehouse Detail）——「干净的业务明细」

| 做了什么 | 效果 |
|---|---|
| **清洗 9 类脏数据** | 姓名尾空格 1,000 条 → `TRIM` 后 0 残留；成绩越界/非数字 → 置 NULL 并标记 |
| **星型建模**：10 维 + 3 事实 | 维度可复用，任何分析都能"从事实表出发、挂维度看" |
| **未知成员占位**（-1） | 脏外键不丢行：`schedule_id=999999` → 指向「未知班次」，JOIN 不丢数据 |
| **有效性标记** `is_valid` + `invalid_reason` | 明细全保留，但无效数据（退课/脏外键/非数字）可被下游过滤，**且知道为什么无效** |
| **学生拉链表**（SCD2，28,000 段） | 能查「2025-06-01 这个学生是休学还是在读」——业务库做不到 |
| **11 条质量规则** → `dq_result` | 共发现 1,687 条问题，每条都有"发现数/修复数/通过率" |

**这一层最值钱的两件事**：
1. **拉链表**：20,000 学生 → 28,000 段（12,000 人 1 段、8,000 人 2 段），支持任意历史时点回溯
2. **清洗可举证**：不是"我洗了"，而是"我洗了 1,687 条，每类多少条、怎么处理的、处理成什么"

### ③ DWS 层（Data Warehouse Summary）——「口径固化的中间层」

| 做了什么 | 效果 |
|---|---|
| 4 张主题宽表（学生/课程/班级/教师 × 学期） | 明细 290 万行 → **6.2 万行**，聚合一次、复用多次 |
| **口径统一写在 SQL 里** | 均分=最高分、挂科=正考<60、折算缺勤=旷课+迟到>30+早退>30 |
| 同时保留两种口径（`avg_score` / `avg_first`） | 学生权益口径 vs 教学评估口径各取所需，不打架 |
| 建索引支持下游 | `idx_class`、`idx_college`，ADS 聚合秒级完成 |

**为什么不能跳过这层直接查 DWD？**
因为"均分取最高分还是正考"这种决策，如果每个报表各写一遍，迟早出现两个报表数字不一致。**DWS 是口径的唯一出处。**

### ④ ADS 层（Application Data Service）——「业务能直接用的指标」

| 指标表 | 谁会用 | 效果 |
|---|---|---|
| `ads_term_kpi` 学期 KPI | 教务处 / 校领导 | 一屏看全校：20,000 学生、14.4 万选课人次、均分 79.5、挂科率 10.4% |
| `ads_course_fail_rank` 挂科率排行 | 教学督导 | 直接定位问题课程（电机学 13.0%、数据结构 12.3%） |
| `ads_student_risk` 学业预警 | 辅导员 | 9,129 人在名单里，分高/中风险，附预警原因 |
| `ads_teacher_workload` 教师工作量 | 人事 / 院长 | 授课班次、学生人次、均分、挂科率 |
| `ads_attendance_weekly` 周趋势 | 学工部 | 每周出勤率趋势（85.0% → 85.2%） |
| `ads_score_distribution` 成绩分布 | 教学评估 | 5 段分布，<60 占 10.41%，与挂科率互相印证 |
| `ads_college_kpi` 学院对比 | 校领导 | 12 个学院横向排名 |
| `ads_term_trend` 多学期趋势 | 规划处 | 3 个学期 KPI 变化折线 |

**效果**：业务方一句 SQL 就能拿到结果，不需要知道"哪张表有多少行、要怎么 JOIN"。

## 五、面试讲这个项目的三段式

**① 问题**：教务数据散在十几个业务表，出"挂科率""缺勤预警"要跨 5 张表手写 SQL，口径还不统一。

**② 方案**：做了四层数仓——ODS 留痕、DWD 清洗建模、DWS 固化口径、ADS 出指标。关键设计是：ODS 全字符串贴源保证不丢脏数据、拉链表支持学籍历史回溯、未知成员占位保证脏外键不丢行。

**③ 结果**：21 张源表 392 万行 → 8 类指标表；11 条质量规则覆盖 1,687 条问题；考勤 192 万行的聚合查询从 39 秒压到 DWS 层一次算完、ADS 查询毫秒级。
