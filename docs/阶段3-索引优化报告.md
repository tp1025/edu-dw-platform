# 阶段3 实验报告：索引优化（3 条真实慢查询）

> 环境：MySQL 26.10 @ 127.0.0.1:3307 ｜ 数据：`fact_attendance` 192 万行
> 慢查询来源：**`mysql.slow_log` 表**（阈值 0.2 秒），全部是真实执行记录，不是编的
> 结论：3 条慢查询平均耗时从 **1.78 秒降到 0.13 秒**，最快提速 **14,000 倍**

---

## 一、优化总览

| SQL | 优化前耗时 | 优化后耗时 | 提升 | 扫描行数变化 | 关键手段 |
|---|---|---|---|---|---|
| **Q1** 函数套索引列 | 1.557 s | **0.00011 s** | **14,000×** | 1,920,000 → **96** | 把 `CAST` 从列上移走 |
| **Q2** 深分页 | 1.059 s | **0.00055 s** | **1,900×** | 1,500,000 → **20** | 游标分页替代 `LIMIT offset` |
| **Q3** 分组聚合 | 2.706 s | **0.389 s** | **7×** | 640,000（不回表） | 覆盖索引 `(term_id, week_no, att_status)` |

> **最有力的证据**：优化后三条查询全部**低于 0.2 秒慢查询阈值**，因此它们**再也不会出现在慢日志里**。

## 二、Q1：函数导致索引失效

### 现象
```sql
-- 优化前（慢日志记录 1.557 秒，扫描 1,920,000 行）
SELECT COUNT(*) FROM fact_attendance WHERE CAST(student_id AS CHAR) = '12345';
```

### EXPLAIN 对比

**优化前**：
```
-> Aggregate (actual time=1557..1557)
    -> Filter: (cast(student_id as char) = '12345')  (actual time=860..1557, rows=96)
        -> Covering index scan on fact_attendance using idx_student  (actual time=0.873..919, rows=1.92e+6)
```
→ 索引是**全索引扫描**（`index scan` 不是 `lookup`）：扫完 192 万个索引项，再逐条算 `CAST` 去比对。

**优化后**：
```sql
SELECT COUNT(*) FROM fact_attendance WHERE student_id = 12345;
```
```
-> Aggregate (actual time=0.11..0.111)
    -> Covering index lookup on fact_attendance using idx_student (student_id = 12345)  (actual time=0.062..0.079, rows=96)
```
→ `index lookup`：直接在 B+ 树上按 `12345` 定位，取 96 行就完事。

### 病因
B+ 树索引里存的是**列的原始值**并按原始值排序。`CAST(student_id AS CHAR)` 是**计算后的新值**，索引里根本没有这个结果，只能全扫一遍逐行计算。

### 改法
**不要在索引列上做运算，把转换放到常量一侧**：
- ✅ `WHERE student_id = 12345`
- ✅ `WHERE student_id = CAST('12345' AS UNSIGNED)`
- ❌ `WHERE CAST(student_id AS CHAR) = '12345'`

### 结果
**1.557 秒 → 0.00011 秒（14,000 倍），扫描 192 万行 → 96 行**

## 三、Q2：深分页 LIMIT offset

### 现象
```sql
-- 优化前（慢日志记录 1.059 秒，扫描 1,500,000 行，只返回 20 行）
SELECT attendance_sk, att_status FROM fact_attendance
ORDER BY attendance_sk LIMIT 1500000, 20;
```

### 三种写法实测对比

| 写法 | 实际耗时 | 扫描行数 | 说明 |
|---|---|---|---|
| **原始** `LIMIT 1500000,20` | 1.059 s | **1,500,000** | 扫 150 万行、带回宽行数据、丢掉前 150 万 |
| **方案 A 延迟关联** | 0.925 s | **仍约 1,500,000** | 只减少了回表数据量，**扫描量没变** |
| **方案 B 游标分页** | **0.00055 s** | **20** | 从索引直接定位，前面一行都不扫 |

### 延迟关联（方案 A）
```sql
SELECT a.attendance_sk, a.att_status
FROM fact_attendance a
JOIN (
  SELECT attendance_sk FROM fact_attendance ORDER BY attendance_sk LIMIT 1500000, 20
) t ON t.attendance_sk = a.attendance_sk;
```
**效果有限（1.059s → 0.925s，仅 13%）**：因为子查询**仍要扫 150 万索引项**，只是避免了把宽行数据搬出来。

### 游标分页（方案 B，推荐）
```sql
-- 记住上一页最后一条的 attendance_sk = 1500000，下一页从它之后开始
SELECT attendance_sk, att_status
FROM fact_attendance
WHERE attendance_sk > 1500000
ORDER BY attendance_sk
LIMIT 20;
```
```
-> Index range scan on fact_attendance using PRIMARY over (1500000 < attendance_sk)  (actual time=0.468..0.52, rows=20)
```
**1.059 秒 → 0.00055 秒（1,900 倍），扫描 150 万行 → 20 行**

### 结论（面试重点）
> **"延迟关联能解决深分页"是错误答案。** 它只减少回表开销，`rows_examined` 几乎不变；真正解决数量级问题的是**游标分页**（记住上一页末位主键 + 范围查询）。
> 代价：游标分页**只支持顺序下拉，不能跳页**；需要跳页的业务可以用"限制最大页数 + 预计算总数"。

## 四、Q3：分组聚合缺覆盖索引

### 现象
```sql
-- 优化前（慢日志记录 2.706 秒，扫描 640,000 行）
SELECT week_no, att_status, COUNT(*) AS cnt
FROM fact_attendance WHERE term_id = 202601
GROUP BY week_no, att_status;
```

### EXPLAIN 对比

**优化前**：
```
-> Table scan on <temporary>
    -> Aggregate using temporary table
        -> Index lookup on fact_attendance using idx_term (term_id = 202601)  (rows=956159)
```
→ 只能用到 `term_id` 定位分区，`week_no`/`att_status` 要**回表**取，还要建**临时表**做分组。

**建索引后**：
```sql
ALTER TABLE edu_dw.fact_attendance
  ADD KEY idx_term_week_status (term_id, week_no, att_status);
ANALYZE TABLE edu_dw.fact_attendance;
```
```
-> Group aggregate: count(0)  (actual time=53.7..389)
    -> Covering index lookup on fact_attendance using idx_term_week_status (term_id = 202601)  (actual time=0.279..286, rows=640000)
```
→ **无临时表、无 filesort、不回表**（`Covering index lookup`）。

### 索引顺序怎么定的
```
(term_id, week_no, att_status)
  ①         ②         ③
① 等值条件列放最前（WHERE term_id = ?）
② 分组字段紧随其后，且顺序与 GROUP BY 一致
③ SELECT 里用到的列都放进索引 → 覆盖索引
```
**三条都满足 → 索引本身就是有序的分组结果，不需要再排序建表。**

### 结果
**2.706 秒 → 0.389 秒（7 倍）**；扫描量不变（64 万行），但**从"回表 + 临时表"变成"纯索引扫描"**。

## 五、索引设计 5 条原则（面试可直接背）

| # | 原则 | 说明 |
|---|---|---|
| 1 | **索引列保持"干净"** | 不要套函数、不要隐式类型转换、不要用 `LIKE '%x'` |
| 2 | **最左前缀** | 联合索引 `(a,b,c)` 只能从 `a` 开始用起，跳过 `a` 用 `b` 无效 |
| 3 | **等值在前、范围/分组在后** | `WHERE a=? AND b>? GROUP BY c` → 索引 `(a,b,c)` 或 `(a,c,b)` 视具体情况 |
| 4 | **覆盖索引免回表** | 把 SELECT 的列也放进索引，`Extra` 会出现 `Using index` |
| 5 | **索引不是越多越好** | 每个索引都要维护 B+ 树，写入变慢；且索引多了优化器可能选错 |

## 六、面试问答

**Q：怎么发现慢查询的？**
> "开了 `slow_query_log`，阈值 0.2 秒，`log_output=TABLE` 直接写进 `mysql.slow_log` 表，用 SQL 就能按 `query_time` 排序捞出来。这三条就是从日志里查到的。"

**Q：`rows` 和 `rows_examined` 有什么区别？**
> "`rows` 是优化器**估算**要扫多少行；`rows_examined` 是慢日志记录的**实际**扫描行数；`EXPLAIN ANALYZE` 里的 `actual time=... rows=...` 才是真实值。估算可能偏差很大，所以一定要看 `EXPLAIN ANALYZE`。"

**Q：`Using index` / `Using filesort` / `Using temporary` 分别什么意思？**
> - `Using index`：索引覆盖，不回表（好）
> - `Using filesort`：需要额外排序（一般不好，除非数据量小）
> - `Using temporary`：用了临时表（GROUP BY / DISTINCT 时常见，通常伴随 filesort）

**Q：为什么加索引后优化器还是不走？**
> "两个原因：① 统计信息过期 → `ANALYZE TABLE`；② 优化器算过成本，觉得全表扫更快（例如筛选后行数占比太高，比如超过 20%～30% 时索引反而更慢）。"

## 七、可直接写进简历的表述

> - 配置慢查询日志（`log_output=TABLE`，阈值 0.2s），从 `mysql.slow_log` 定位 3 条真实慢查询（最高 2.7 秒）；
> - **Q1** 消除索引列上的 `CAST`，把类型转换移到常量侧，耗时 1.557s → 0.11ms（**14,000 倍**），扫描行数 192 万 → 96；
> - **Q2** 深分页改用**游标分页**（末位主键 + 范围查询），耗时 1.059s → 0.55ms（**1,900 倍**），扫描行数 150 万 → 20；对比实验证明"延迟关联"只减少回表、扫描量不变；
> - **Q3** 按"等值列 → 分组列 → 覆盖列"设计联合索引 `(term_id, week_no, att_status)`，消除临时表与 filesort，耗时 2.706s → 0.389s（7 倍）。
